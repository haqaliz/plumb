## What this proves

- **Resolve → execute → capture is wired end to end against a real environment.** The
  notebook-only checkout resolved via the fallback rule; the runner executed the checkout's
  own `jupyter nbconvert --to notebook --execute --inplace`; capture stored the executed
  notebook whole-file (`kind=notebook`, 2 cells) plus one `notebook_cell` artifact carrying
  the kernel's actual output (`AUC = 0.91`, 67 bytes of canonical JSON). The two `bytes`
  objects are stdout (930 B — nbconvert's progress log, not claim data) and empty stderr.
- **The claim-level loop still needs the C4 locator.** The paper is vacuous (0 claims) on
  purpose: with no `notebook_cell` locator there is nothing to bind a claim to yet. This probe
  is the precondition, not the verdict (`docs/planning/binding-verdict/prd.md:238`).
- **The cell projection is the stable artifact; the whole notebook is provenance.** Across the
  two probe runs the `notebook_cell` sha was identical (`eaa1cfdb8f95da17…`, 67 bytes) while
  the whole-file notebook sha moved (`b34edb5d7c1a864e…` → `d7ba7753ab34ff3a…`, same 1088-byte
  size): nbconvert's in-place execution rewrites notebook metadata that varies even when the
  outputs are identical. So a live notebook run's `run_id` legitimately differs run-to-run
  (execution is a per-run fact), while per-cell output projections are the hash-stable,
  bindable evidence. Observed on two runs only; stated as observed, not as a general law.
- Note the run dir (`run-252cb556cd59-ddd498b8`) is identical across the two runs: the
  checkout tree hash and argv are deterministic, so the CLI's run slot is too.
