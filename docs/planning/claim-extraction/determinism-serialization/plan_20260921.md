## 0. Open questions, now closed

| Question | Decision | Rationale |
|---|---|---|
| `.87` vs `0.87` — one claim or two? | **Two.** Pure string identity, unchanged from M13. | "Same characters = same claim" is reimplementable from one sentence, which C6's independent replay requires. Any normalization must be documented and versioned. If double-counting shows up in labelled papers, revisit on evidence — the same principle applied to hyphen ranges. |
| Hash algorithm | **`sha256`**, recorded explicitly in the output and in a named constant. | Obvious default; the requirement is that it is *recorded*, not that it is clever. C6 replay depends on knowing it. |
| Schema/tool version in output? | **No.** | Keeps the contract `input → bytes`, forever. Version/provenance belongs in C6's bundle envelope. Embedding it would make every determinism assertion carry a version caveat. |

**Clarification (the hash algorithm is not a "version field").** Recording
`PAPER_HASH_ALGORITHM` in the output does **not** violate row 3. A version field changes
the bytes for unchanged input *gratuitously* — the content is identical, only the stamp
moved. The algorithm name is never the sole cause of a byte difference: if it changes,
the digest has already changed. It is a label on a value that already differs, which
makes it categorically unlike a version.

**But record it, never parameterize it.** Making the algorithm a parameter adds a second
input, and "identical input → identical bytes" silently becomes "identical input *and
callers who agree* → identical bytes". Two call sites passing different values would
produce different bytes for the same claims. The algorithm is a constant, imported.

**Consequence for Phase 1 (applied):** `hash_paper` returns the digest and its algorithm
as one inseparable record, not a bare hex string. A digest is uninterpretable without its
algorithm, so the two must not travel apart — and a digest that arrives from elsewhere
and gets stamped `"sha256"` by the serializer would be *mislabeled*, which is worse than
unlabeled: a replayer is told how to verify it and the instruction is wrong.

**Do not revisit these in code.** If an agent believes one is wrong, stop and report.

## 1. Design decisions this plan commits to

### D1 — Serialization is a pure function, and nothing in it reads ambient state

No `datetime`, no `os.getcwd()`, no `Path.resolve()`, no `uuid`, no `random`, no
environment variables, no locale-sensitive calls. Determinism is achieved by *not
having* sources of nondeterminism, not by scrubbing them afterwards.

### D2 — Sort by an explicit total key, never by insertion or hash order

Claims serialize in a defined order. A total key means no tie can fall back to
nondeterministic ordering. `sorted()` is stable, but stability only preserves an input
order that may itself be nondeterministic — so the key must be total, not partial.

**Corrected 2026-09-21.** An earlier draft spelled the key
`(reported_value.text, metric, units or "", location.start, location.end)`. The
`units or ""` term is a bug: it maps `units=None` and `units=""` to the same sort
value, collapsing a distinction aspect 1 deliberately preserves (`Claim.id` separates
them with a presence tag). Two claims differing only in that field would then have no
defined relative order — precisely the nondeterminism this aspect exists to remove.

Sort presence separately from value, e.g.
`(reported_value.text, metric, units is None, units or "", <location key>)`. The
requirement is not the spelling but the property: **no two distinct claims may tie on
the full key.**

**Second correction, same draft.** The location term was spelled
`location.start, location.end`. Those attributes live on `CharSpan`, **not** on the
`Location` base — and `Location` is a union precisely so a `PageBox` variant (PDF page +
bbox) can join without a schema migration. This key would have prevented that: when
`PageBox` lands, either the serializer raises `AttributeError`, or — if someone gives
`PageBox` a `start` for convenience — page-1 boxes sort against character offsets and
ordering becomes **silently meaningless while the suite stays green**. The silent
failure is the dangerous one.

Key on `(kind, start, end)` with the **variant tag leading**, so a second variant orders
*against* `CharSpan` rather than colliding with it. `CharSpan` already carries a `kind`
`ClassVar` discriminator for exactly this purpose. An unknown variant must **raise**,
naming the sort-key function as the thing to extend — never fall back to arrival order,
which reintroduces the extraction-order dependence this aspect removes.

`dedup.py` implements this as `_location_sort_key`. Serialization must match it rather
than invent a second spelling: two modules ordering locations differently is its own bug.

### D3 — Dedup merges *locations*, never values

A merged claim carries one `reported_value` and a **sorted tuple of locations**. The
`id` is unchanged by the merge — aspect 1 already guarantees this by excluding
`location` from the id derivation. This is the property that makes dedup safe.

### D4 — The paper hash covers the normalized text

`normalize_text(raw)` encoded UTF-8, then sha256. The same bytes the offsets index. A
CRLF-vs-LF difference must not change the hash; a character change must.

## 2. Implementation phases

### Phase 1 — Paper hash (M6)

- **Goal:** a named, recorded content hash over normalized text.
- **Prerequisites:** none beyond merged aspect 1.
- **RED first:** CRLF/LF twins hash identically; a one-character change does not; the
  algorithm name is exposed, not implicit.
- **Files:** `src/plumb/extract/hashing.py`, `tests/extract/test_hashing.py`
- **Exports:** `PAPER_HASH_ALGORITHM = "sha256"`, `hash_paper(raw: str) -> PaperHash`
  (a frozen record carrying `digest` + `algorithm`, per the §0 clarification — **not** a
  bare hex string). `algorithm` is `init=False` and derived from the constant, which
  makes a mislabeled digest *unrepresentable* rather than merely rejected.
- **Rules:** hash the **normalized** text, not the raw input. Domain-separate the digest
  (aspect 1 used `b"plumb.claim.id.v1"`; use an analogous `b"plumb.paper.v1"` prefix) so
  a paper digest cannot collide with a claim digest over the same bytes. Full untruncated
  hex.
- **Validation:** `uv run pytest tests/extract/test_hashing.py`
- **Commit:** `Add paper hash over normalized text with named algorithm`

### Phase 2 — Deterministic serialization (M6, M9)

- **Goal:** identical input → identical bytes, across processes.
- **Prerequisites:** Phase 1.
- **RED first:** the two-process test (below) is the load-bearing one — write it first
  and watch it fail.
- **Files:** `src/plumb/extract/serialize.py`, `tests/extract/test_serialize.py`
- **Exports:** `serialize_claims(claims, *, paper_hash: PaperHash) -> bytes`,
  `SERIALIZATION` constant recording the pinned options. `paper_hash` is the **record**
  from Phase 1 carrying both algorithm and digest — not a bare hex string, so the
  serializer cannot stamp an algorithm onto a digest it did not produce. The output
  records both; see the §0 clarification for why that is not a version field.
- **Rules:**
  - `json.dumps` with **every** option pinned explicitly: `sort_keys=True`,
    `ensure_ascii=False`, `separators=(",", ":")`, `indent=None`, plus an explicit
    trailing newline. Pin them as a named constant so a reader sees the contract rather
    than inferring it from call sites.
  - Returns **`bytes`** (UTF-8), not `str`. "Byte-identical" must be asserted on bytes;
    asserting on `str` leaves the encoding unpinned.
  - Output ordering per D2.
  - No timestamp, no absolute path, no version field (§0).
  - `Decimal` serializes via its **verbatim `text`**, never `float(...)`. A `Decimal` is
    not JSON-serializable and the default coercion is to float — that would silently
    reintroduce R2 at the last possible moment. Use an explicit encoder that refuses
    unknown types rather than one that falls back.
- **Validation:** `uv run pytest tests/extract/test_serialize.py`
- **Commit:** `Add deterministic byte-identical serialization for claims`

### Phase 3 — Value-identity dedup (M13)

- **Goal:** merge duplicate mentions of one result without merging distinct values.
- **Prerequisites:** none beyond merged aspect 1 (independent of Phase 2 — see §3).
- **RED first:** the `0.87` / `0.870` boundary test and the `.87` / `0.87` test (which
  per §0 must remain **two** claims).
- **Files:** `src/plumb/extract/dedup.py`, `tests/extract/test_dedup.py`
- **Exports:** `dedup_claims(claims) -> tuple[MergedClaim, ...]`, plus `MergedClaim`,
  `claim_identity`, `group_claims`, `merged_locations`. (The representation question in
  §7 assumption 1 was resolved in favour of a distinct `MergedClaim`.)
- **Rules:** merge only on byte-identical `reported_value.text` **and** identical
  `metric` and `units` — i.e. on the same basis the `id` is derived from, so
  "same id ⇒ merged" holds exactly. Locations sort by `(start, end)`.
- **Validation:** `uv run pytest tests/extract/test_dedup.py`
- **Commit:** `Add value-identity dedup merging locations not values`

### Phase 4 — Determinism controls as enforced tests (M9)

- **Goal:** the controls that a Python pipeline breaks by default, pinned by tests
  rather than by discipline.
- **Prerequisites:** Phases 1–3.
- **Files:** `tests/extract/test_determinism.py`
- **Required tests:**
  - **Two-process byte-identity under at least two different `PYTHONHASHSEED` values**
    (subprocess, compare stdout bytes). This is the load-bearing test — a single-process
    test passes while the contract is broken.
  - Serialized bytes contain no timestamp-shaped and no absolute-path-shaped content.
  - A source-level guard: no `set` iteration feeding output order, no bare `hash()`, no
    `float(` in `src/plumb/extract/`. A grep-style test is crude but catches the
    regression that matters, and aspect 1 already proved the `float` trap is real.
  - `.gitattributes` still carries `eol=lf` (it was pulled forward in aspect 1;
    assert it rather than assume it).
- **Note:** the subprocess test needs the network-blocking autouse fixture to not
  interfere. `subprocess` is explicitly outside the guard (documented in `conftest.py`),
  so this works — but confirm rather than assume.
- **Commit:** `Pin determinism controls with cross-process tests`

## 4. Testing strategy

- Written first, per phase, lifted from `spec.md`'s acceptance criteria.
- `uv run pytest` after every task; the suite must stay green at 209 + new.
- The **two-process** test is the one that actually proves the contract. Treat a
  single-process pass as insufficient evidence.
- No network (autouse fixture); `subprocess` is used only to spawn a fresh interpreter
  with a different hash seed, never to reach outward.

## 5. Edge cases

| Case | Expected handling |
|---|---|
| Empty claim list | Serializes to a stable, valid, non-empty document — not `b""`. Assert it. |
| `units=None` vs `units=""` | Must serialize distinguishably — aspect 1's id already distinguishes them; serialization must not collapse them. |
| Non-ASCII in `text` (é, en dash, μ) | `ensure_ascii=False` keeps it literal; byte-identity asserted on UTF-8 bytes. |
| A `Decimal` reaching the encoder | Serialize from verbatim `text`; the encoder **refuses** unknown types rather than coercing. |
| Two claims identical in every field including location | Merge to one with one location, not one with a duplicated location. |
| Claims differing only in `units` | Stay separate (their ids differ). |

## 6. Agent execution notes

**Checkpoint:** after Phase 2 — the serialized form is the contract C6 bundles and a
third party replays. Review before dedup and the determinism suite build on it.

**Likely to need iteration:** the two-process test's plumbing (spawning an interpreter
with a set `PYTHONHASHSEED`, getting bytes back uncorrupted — do not let the shell
re-encode or strip a trailing newline).

**Stop and ask before proceeding if:**
- Determinism seems to require scrubbing a timestamp or path *after* generating it —
  per D1 the answer is to not generate it.
- Dedup seems to require a canonical numeric form — §0 closed this; it is `DIVERGED`-risk
  (R2) and the answer is no.
- A verdict (`REPRODUCED`/`DIVERGED`/`UNVERIFIED`) seems needed — this aspect emits none.

## 7. Assumptions

1. Merged claims are represented by adding a locations collection rather than a new
   type. **This needs a decision in Phase 3** — aspect 1's `Claim` has a single
   `location` field, so either `Claim` grows a `locations` tuple (a schema change to a
   merged, already-shipped record) or dedup returns a distinct `MergedClaim`. The plan
   does not pre-judge it; the Phase 3 agent must surface the tradeoff and stop rather
   than silently changing `Claim`.
2. `tests/extract/` layout continues from aspect 1.
