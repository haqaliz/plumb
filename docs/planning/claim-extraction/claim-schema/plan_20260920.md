## 0. Design decisions this plan commits to

Two decisions the spec implies but does not state. Both are load-bearing; an agent
must not silently choose otherwise.

### D1 — `ClaimValue` is a tagged union, not a scalar

The spec's five required round-trip formats are five *kinds* of value, not five
spellings of one:

| Fixture | Kind |
|---|---|
| `0.87` | `Point` |
| `p < 0.001` | `Bound` (operator + magnitude) |
| `0.85 ± 0.03` | `PlusMinus` (center + margin) |
| `95% CI [0.81, 0.89]` | `Interval` (low, high) |
| `12–15%` | `Range` (low, high) |
| `~10,000` | `Approximate` |

This abstraction is **earned, not speculative** — there are already six concrete cases.
Every variant carries the original `text` verbatim plus its `Decimal` component(s).

### D2 — The claim `id` excludes `location`

Aspect 3 requires the `id` to be "unchanged by a location merge"
([`../determinism-serialization/spec.md`](../determinism-serialization/spec.md)). So
`id` is derived from `(reported_value.text, metric, units)` — **never** from
`location`. Deriving it from location would make dedup change identity, which is
circular.

`id` uses `hashlib.sha256` over a pinned field ordering. Aspect 3 owns *recording* the
algorithm and the cross-process stability test; aspect 1 only needs it deterministic
within a process.

  is aspect 2's concern.

### Phase 2 — `ClaimValue` tagged union (M2)

- **Goal:** values that cannot silently lose precision.
- **Prerequisites:** Phase 1.
- **RED first:** parametrized round-trip test over all six fixtures in D1, plus the
  `0.870 != 0.87` test and the no-float assertion.
- **Files:** `src/plumb/extract/value.py`, `tests/extract/test_value.py`
- **Key exports:** `ClaimValue` (base), `Point`, `Bound`, `PlusMinus`, `Interval`,
  `Range`, `Approximate`, `parse_value(text: str) -> ClaimValue | None`.
- **Rules:**
  - Every variant stores `text: str` **verbatim**, exactly as it appeared.
  - Numeric components are `Decimal(str)` — **never** `float(...)`, never
    `Decimal(float)`.
  - **Significant figures do NOT survive `Decimal.__eq__`.** `Decimal("0.870") ==
    Decimal("0.87")` is `True` — Decimal compares numerically, not representationally.
    (An earlier draft of this plan asserted the opposite; it was wrong.) Sig figs
    survive in two places: the verbatim `text` field, and `Decimal.as_tuple()`, whose
    exponent differs (`-3` vs `-2`). Assert on **those**, never on raw `Decimal`
    equality.
  - Consequence for aspect 3: **value-identity must be the verbatim `text`**, not the
    `Decimal`. If dedup rested on `Decimal` equality it would silently merge `0.87` and
    `0.870` — exactly the M13 boundary case that must stay two claims.
  - Comma separators (`~10,000`) and en-dash ranges (`12–15%`) must parse; the en dash
    `U+2013` is not a hyphen.
- **Validation:** `uv run pytest tests/extract/test_value.py`
- **Commit:** `Add ClaimValue union preserving verbatim text and Decimal precision`

### Phase 3 — `Location` tagged union (M7)

- **Goal:** a span that round-trips to the exact source text.
- **Prerequisites:** Phase 1.
- **RED first:** `normalized_text[loc.start:loc.end] == expected_span`, plus a CRLF/LF
  twin test producing identical offsets.
- **Files:** `src/plumb/extract/location.py`, `tests/extract/test_location.py`
- **Key exports:** `Location` (base), `CharSpan(start: int, end: int)`,
  `normalize_text(raw: str) -> str`.
- **Rules:**
  - Offsets are **character** offsets into the **normalized** text — state this in the
    docstring; it is the contract C6's paper hash depends on.
  - `normalize_text` does exactly: CRLF→LF, then Unicode NFC, **once**. Nothing else —
    no dehyphenation, no whitespace collapsing (those change offsets and are not needed
    for text/Markdown input).
  - `Location` is a union *now*, with `CharSpan` its only variant, so aspect-2 PDF work
    can add `PageBox` without a migration.
- **Validation:** `uv run pytest tests/extract/test_location.py`
- **Commit:** `Add Location union with char spans over normalized text`

### Phase 4 — `Claim` record (M1, M8)

- **Goal:** the record every later aspect constructs.
- **Prerequisites:** Phases 2 and 3.
- **RED first:** construction fails without each required field; `tolerance_hint`
  accepts `None`; `id` is stable; **`Claim` has no `confidence` attribute**.
- **Files:** `src/plumb/extract/claim.py`, `tests/extract/test_claim.py`
- **Fields:** `reported_value: ClaimValue`, `units: str | None`, `metric: str`,
  `location: Location`, `artifact_hint: str | None`, `tolerance_hint: str | None`,
  `id: str` (derived).
- **Rules:**
  - Frozen dataclass; `id` computed in `__post_init__` per D2.
  - `units` is nullable — dimensionless metrics exist (an AUC has no unit). The PRD's
    open question on `%` vs percentage-points is **not** resolved here.
  - **The `confidence` negative test is a guardrail, not a style check**
    (`CLAUDE.md` #1) — its docstring must say so, or a future contributor will
    "helpfully" add the field.
- **Validation:** `uv run pytest tests/extract/test_claim.py`
- **Commit:** `Add Claim record with derived id and no confidence field`

### Phase 5 — `StudyParameter` record (M11, shape only)

- **Goal:** the C7-bound record type, distinct from `Claim`.
- **Prerequisites:** Phase 4.
- **RED first:** a `StudyParameter` is not a `Claim` and is not accepted where a
  `Claim` is required.
- **Files:** `src/plumb/extract/study.py`, `tests/extract/test_study.py`
- **Key exports:** `StudyParameter(name: str, value: ClaimValue, location: Location)`.
- **Rules:** shape only — **population is aspect 2's job.** Kept minimal because its
  real consumer (C7) does not exist yet.
- **Validation:** `uv run pytest`
- **Commit:** `Add StudyParameter record distinct from Claim`

## 5. Environment & determinism

- Local setup: `uv sync` (then `uv sync --frozen` in CI).
- No environment variables. No BYOK key. No `.env`. No external service.
- Determinism obligations *in this aspect*: `Decimal` never constructed from `float`;
  `id` hashing over a pinned field order; `normalize_text` applied exactly once;
  `eol=lf`.
- Full determinism controls (cross-process `PYTHONHASHSEED`, serialization byte-pinning,
  no-timestamp/no-abspath assertions) are **aspect 3** — do not implement them here, but
  do not violate them either.
- **Freshness guard and the `UNVERIFIED` cause vocabulary are C3/C4 concerns.** This
  aspect emits **no verdicts of any kind** — if an agent finds itself writing
  `REPRODUCED`, `DIVERGED`, or `UNVERIFIED`, it has left the aspect and must stop.

## 6. Edge cases

| Case | Expected handling |
|---|---|
| `p < 0.001` | `Bound(op="<", magnitude=Decimal("0.001"))` — **never** collapsed to `0.001` (R2) |
| `0.870` vs `0.87` | Distinct values; never normalized together |
| `~10,000` | `Approximate`; comma stripped for the `Decimal`, `text` keeps it verbatim |
| `12–15%` | `Range`; en dash `U+2013`, not a hyphen |
| `95% CI [0.81, 0.89]` | `Interval`; the leading `95%` is the *confidence level*, not the value |
| Unparseable numeric text | `parse_value` returns `None`; **the caller decides** — aspect 1 never invents a value. Emitting a non-claim record with a cause is aspect 2's M4 job |
| Dimensionless metric | `units=None` is legal, not an error |
| Empty / whitespace-only text | `parse_value` returns `None` |

## 7. Agent execution notes

**Checkpoints for human review:**
1. After Phase 2 — D1's union shape is the aspect's biggest design bet. Review before
   Phases 4–5 build on it.
2. After Phase 4 — the `Claim` record is the contract C4 consumes; a mistake here is a
   breaking change later.

**Likely to need iteration:**
- `parse_value`'s regex set. `re` is leftmost-first, so **alternation order changes
  which variant wins** — e.g. `12–15%` must not match `Point` on `12` first. Order
  most-specific-first and add a test per precedence pair.
- The `95% CI [...]` fixture has two plausible readings; the table above fixes one.

**Stop and ask before proceeding if:**
- A phase seems to require a float anywhere in the value path — it does not; that is R2
  and the answer is always `Decimal`.
- A phase seems to require selection logic ("is this number a claim?") — that is
  aspect 2, and pulling it forward would bypass the M15 label-first ordering.
- Serialization or a paper hash seems needed — that is aspect 3.
