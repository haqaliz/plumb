## 0. The split, and why

Spec item 1 (blind labels) and item 2 (the selection rule) are a **blocked pair**. M15
requires the labels to be committed *before* the rule is authored, so that precision and
recall measure whether the rule is right rather than whether the code implements it. If
one author writes both, the metric cannot fail. That is G1, and it was resolved in
favour of label-first.

So this aspect ships in two parts:

| Part | Contents | Blocked? |
|---|---|---|
| **1 (this plan)** | M12 table parsing · M5 admission gate · M4 non-claim records · M11 `StudyParameter` population · the **candidate-extraction + labelling harness** | No |
| **2 (later)** | M3 selection rule · M15 scoring against the committed labels | Yes — needs the owner's labels |

Part 1 deliberately includes the harness that makes part 2 cheap: candidate extraction
finds *every* number with its context and emits a labelling file. The owner marks
claim / not-claim. Those marks become the committed blind labels, and only then is the
rule written.

**Candidate extraction is not selection.** It answers "what numbers are here", never
"which are claims". Keeping them separate is what preserves the ordering M15 requires.

## 1. Design decisions

### D1 — The admission gate is the sole constructor of a `Claim`

No code path may build a `Claim` except through deterministic grounding against the
paper text. The BYOK proposer is out of scope, but the seam it will plug into is built
now: if the deterministic core constructs records directly, the future proposer gets a
second path that bypasses grounding (`ARCHITECTURE.md:59-61`, `CLAUDE.md` #4).

### D2 — Ungroundable candidates surface with a named cause

Never a `Claim`, never a verdict, never silent. A silent drop is indistinguishable from
a claim that was never there, and it flatters the coverage number the Phase 0 gate rests
on. The cause vocabulary here is **extraction-side and separate** from C4's
`UNVERIFIED` causes — this aspect emits no verdicts and must not borrow verdict
vocabulary.

### D3 — Candidate extraction is exhaustive and dumb

It finds every number, records where and what surrounds it, and judges nothing. Its
output is the labelling file's input. Over-extraction here is correct; the selection
rule is what narrows later.

## 2. Phases

### Phase 1 — Markdown table parsing (M12)

- **Goal:** cells located precisely enough to cite.
- **Files:** `src/plumb/extract/tables.py`, `tests/extract/test_tables.py`
- **Rules:** a cell's `CharSpan` must round-trip to the cell's own text, not the row's.
  Pipe tables with and without a leading/trailing pipe; alignment rows are structure,
  not data; a cell may be empty; escaped pipes (`\|`) are not delimiters.
- **Out of scope:** deciding whether a cell is a claim.
- **Commit:** `Parse Markdown tables into located cells`

### Phase 2 — Candidate extraction (harness for M15)

- **Goal:** every number in a paper, with context, deterministically ordered.
- **Files:** `src/plumb/extract/candidates.py`, `tests/extract/test_candidates.py`
- **Rules:** a `Candidate` carries the matched text, its `CharSpan`, the surrounding
  sentence or cell, and a coarse section hint (abstract / results / table / references /
  other) derived **structurally** from Markdown headings — never by guessing meaning.
  Exhaustive by construction. Deterministic order via the shared `ordering` helpers.
- **Commit:** `Extract every numeric candidate with its context`

### Phase 3 — Admission gate + non-claim records (M5, M4)

- **Goal:** the only door a `Claim` comes through.
- **Files:** `src/plumb/extract/admit.py`, `tests/extract/test_admit.py`
- **Rules:** `admit(candidate, ...) -> Claim | NonClaim`. Grounding is re-checking that
  the candidate's span still yields its text in the normalized paper — a candidate
  whose span does not round-trip is `NonClaim(cause=UNGROUNDED)`. `NonClaim` carries a
  named cause from a closed vocabulary and is never a `Claim` (no shared base beyond
  `object`, mirroring `StudyParameter`).
- **Commit:** `Add admission gate as the sole constructor of a Claim`

### Phase 4 — `StudyParameter` population (M11)

- **Goal:** reported N extracted, and kept out of the claim denominator.
- **Files:** extend `src/plumb/extract/admit.py`, `tests/extract/test_study_population.py`
- **Rules:** recognise `n = 412`, `N=412`, `(n = 412)`. Emits `StudyParameter`, never a
  `Claim`. A test asserts N never appears in claim output.
- **Commit:** `Populate StudyParameter from reported sample sizes`

### Phase 5 — Labelling file emitter

- **Goal:** make the owner's labelling step cheap and its output committable.
- **Files:** `src/plumb/extract/labelling.py`, `tests/extract/test_labelling.py`
- **Rules:** emit one row per candidate — id, text, section hint, surrounding context,
  and an empty `claim` column for the human. Deterministic; round-trips back in so the
  filled file is loadable as the blind label set. **The emitter never writes a value in
  the `claim` column**, not even a suggestion: a pre-filled guess anchors the labeller
  and re-introduces the circularity by the back door.
- **Commit:** `Emit and load the blind labelling file`

## 3. Testing

`uv run pytest`, no network, test-first throughout. The existing repo-wide AST guard in
`test_determinism.py` covers new modules automatically via `rglob` — it will fail on a
`float(`, a bare `hash(`/`id(`, or a non-allowlisted import in anything added here.

**Note for every phase:** this aspect emits **no verdicts**. If an agent writes
`REPRODUCED`, `DIVERGED` or `UNVERIFIED`, it has left the aspect.

## 4. Out of scope

The selection rule (part 2), PDF, DOI, the BYOK proposer, serialization/hashing/dedup
(aspect 3), the record field set (aspect 1).

## 5. Open

- Section-hint granularity: structural Markdown headings only for now. A paper without
  headings gets `other` for everything, which is honest rather than guessed.
- The labelling file format (CSV vs JSONL) — Phase 5 decides; it must be diff-friendly
  in git, since the labels are committed evidence.
